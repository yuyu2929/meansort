# 基准测试

本文件记录 MeanSort 的性能数据、测量方法，以及 2.0 → 2.1 的算法改动到底带来了什么。

所有数字都可以从 GitHub Actions 的日志里逐次复现，命令见文末。

## 环境与方法

| 项 | 值 |
|---|---|
| 机器 | GitHub Actions `ubuntu-latest`，本次 run 为 4 vCPU |
| 编译器 | g++ 13，`-O3 -std=c++17 -pthread` |
| 数据类型 | `long long` |
| N | 2,000,000 |
| 计时 | `std::chrono::steady_clock`，包裹整个排序调用，**含数据拷贝外的全部开销** |
| 正确性 | 每次测量后与 `std::sort` 结果逐元素比对，不一致会打印 `(正确性 FAIL!)` |
| 随机种子 | 固定 42，同一 run 内新旧算法吃完全相同的数据 |

**关于噪声**：每个用例只测一次，没有做多次取中位数。CI runner 的数字波动通常在 ±5% 左右，
**所以请只比较同一次运行内的相对关系，不要跨 run 比绝对值**。
另外 CI 分配的核数会变（见过 2 核也见过 4 核），并行列的数字随之变化。

## 2.1 vs 2.0：同机 A/B

2.0 的问题是：**对任何数据都用三路划分**，于是每个元素最坏要比较两次
（`a < pivot` 一次、`pivot < a` 一次）。

2.1 在采样时顺便统计中间段的等值对密度，低重复度数据改走两路 Hoare 划分
（每元素约 1 次比较），高重复度数据保留三路划分。

为了让这个改动可验证，仓库里保留了一个**仅供对比的编译开关** `MEANSORT_ALWAYS_THREE_WAY`
（CMake 选项 `MEANSORT_BUILD_BENCH_LEGACY`），它会强制回到 2.0 的行为。
两个二进制在同一次 CI 运行里跑同一份数据，于是下面的对比是可信的。

单位：毫秒（ms），N = 2,000,000

| 数据分布 | std::sort | 2.0 串行 | **2.1 串行** | 2.0 并行 | **2.1 并行** |
|---|---|---|---|---|---|
| 均匀随机 | 133.1 | 184.0 | **177.3** | 86.1 | **76.9** |
| 指数分布（重尾） | 136.6 | 180.7 | **177.4** | 87.0 | **74.2** |
| 对数正态（重尾） | 134.5 | 182.6 | **174.7** | 93.6 | **87.1** |
| 少量离群点 | 80.8 | 72.7 | 73.0 | 45.7 | 45.9 |
| 大量重复（100 种值） | 60.5 | 45.4 | 45.3 | 31.7 | 32.8 |
| 已排序 | 20.5 | 0.7 | 1.3 | 31.2 | **4.1** |
| 逆序 | 14.8 | 1.2 | 1.1 | 28.6 | **4.2** |
| 等比数列（最坏构造） | 42.7 | 23.9 | **22.6** | 14.9 | **11.3** |

### 怎么读

**1. 自适应划分的收益比预期小。**
均匀随机串行 184.0 → 177.3，只有 **约 4%**；重尾分布几乎没变。
说明"每元素两次比较"不是单线程落后的全部原因——采样开销（16 个元素做插入排序）、
划分本身对缓存的访问模式，同样是成本。这是诚实的结论：**这次改动没把单线程追平**。

**2. 单线程仍然比 `std::sort` 慢约 33%。**
177.3 vs 133.1。这是当前事实。任何"MeanSort 比 std::sort 快"的说法，都必须限定在
特定场景（重复值、有序输入、最坏构造）或并行条件下，否则不成立。

**3. 真正的优势在并行。**
4 核上均匀随机 76.9 vs 133.1 = **1.73 倍**，重尾 74.2 vs 136.6 = **1.84 倍**。
这部分不依赖算法微调，只依赖"别人没有开箱即用的并行排序"这个事实。

**4. 有序/逆序的并行版是这次改动的意外收获。**
旧并行版 31.2 ms，新并行版 4.1 ms。原因：旧版用 2×线程数 个线程抢块、块划分也更多，
有序数据被切碎后每个块都要重新做早退扫描；新版线程数等于核数、块更少，早退更有效。
不过仍然比串行（1.3 ms）慢，并行在这类输入上没有意义。

**5. 重尾分布是已知未解问题。**
指数分布串行 177.4，比 `std::sort` 的 136.6 慢 30%。根因不在划分策略，而在**枢轴估计**：
截尾均值在右偏分布下会被长尾拉高，导致切分不平衡。要修就得把枢轴从"均值"换成
"截尾中位数"，那会改变本库的设计前提，因此列为待决策项而非直接改动。

## 复现

```bash
cmake -B build \
  -DMEANSORT_BUILD_BENCH=ON \
  -DMEANSORT_BUILD_BENCH_LEGACY=ON \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release

./build/meansort_bench 2000000          # 当前版本
./build/meansort_bench_legacy 2000000   # 2.0 行为（恒定三路划分）
```

CI 每次 push 都会跑这两条，日志在 [Actions](https://github.com/yuyu2929/meansort/actions) 页面可查。

## 未做的测量（避免过度声称）

- 没有与 **GNU parallel mode**（`-fopenmp` + `__gnu_parallel::sort`）对比；
- 没有与 **TBB**（`tbb::parallel_sort`）对比；
- 没有与 **pdqsort** 对比；
- 没有做多次取中位数、没有统计方差；
- 没有覆盖 `int` / `float` / `double` 的完整矩阵（仅 `long long` 与 double 正确性测试）。

在这些补齐之前，本文的数字只能支撑"同类实现之间同机对比"这一个结论，
不足以支撑"业界最快"之类的断言。
