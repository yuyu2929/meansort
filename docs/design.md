# 设计决策记录

这份文档记录 MeanSort 里那些**不显然的选择**：为什么这么做、代价是什么、当时否掉了什么。
写它的目的有两个：让读代码的人少走弯路，也让作者在面试或答辩时能讲清楚每个数字的来历。

> 标注为 **【待补充】** 的地方，是我（代码整理者）无法从代码和提交历史中推断的部分，
> 需要作者本人补上真实动机。不要编造——面试官追问细节时，编的东西一定会露馅。

---

## 0. 目标与非目标

**目标**

- 内存内、大规模、**数值型**数组的排序；
- 开箱即用的多线程，不需要使用者改编译参数或引入第三方依赖；
- 最坏情况有硬保证，不能被构造性输入打爆；
- 单文件集成，降低采用成本。

**非目标（明确不做）**

- 不支持自定义类型与比较器（枢轴依赖算术运算）；
- 不追求稳定排序；
- 不做外部排序（数据放不进内存的场景不在范围内）；
- 不追求在"均匀随机单线程"上打赢 `std::sort`——这一点后面有专门的决策说明。

## D1. 枢轴：截尾均值，而不是中位数或 median-of-three

**做法**：等距取 16 个样本 → 小排序网络排好 → 去掉两端各 4 个 → 中间 8 个求算术平均
（用 `long double` 累加，再转回 `T`）作为枢轴；采样起点加随机相位。

**理由**

- 均值对对称分布是良好估计，且比中位数更平滑（不会因为采样偶然性跳到某个极值）；
- 掐掉两端各 4 个，等于丢掉最极端的 25%，让重尾/离群点无法直接把枢轴拽走；
- 16 个样本里至少 4 个 ≤ 枢轴、4 个 ≥ 枢轴，保证两个方向都非空，划分不会退化。

**代价（实测，见 [benchmark.md](benchmark.md)）**

- 右偏分布（指数、对数正态）下，**均值会被长尾拉高**，切分不平衡，串行比 `std::sort` 慢约 30%；
- 采样本身有成本：16 个元素做插入排序约 60 次比较，而 `std::sort` 的 median-of-three 只要 3 次。

**如果重来**

换成"截尾中位数"（取中间 8 个里的中位）几乎必然改善重尾表现，但会改变项目的设计前提
（"统计枢轴=均值"是命名与叙事的根基），因此列为待决策项而不是直接改。

**【待补充】** 最初为什么选均值而不是中位数？是出于对称分布的设想，还是先写了均值再发现重尾问题？

## D2. 划分：自适应两路/三路，而不是恒定三路

**背景**

2.0 对所有数据都用三路划分（荷兰国旗）。三路划分每个元素最多比较两次：
`a < pivot` 一次，为假时再比 `pivot < a` 一次。均匀随机数据里等值元素极少，
这第二比较几乎是纯浪费。

**做法**

采样时顺手统计中间 8 个样本里"相邻相等"的对数，作为**低基数探针**：

- 等值对 `>= 2` → 判为高重复度，走三路划分（等值区整层排除，收益是真的）；
- 否则 → 走两路 Hoare 划分，每元素约 1 次比较。

阈值取 2 的原因：中间段只有 7 个相邻对，取 1 会被单次偶然相等误判，
取 3 以上会漏掉"每 4 个值里出现一次重复"这类真实的高重复数据。**这是经验值，不是推导出来的。**

**代价**

- 同机 A/B 实测，串行只快了约 4%（184.0 → 177.3 ms，均匀随机），**没有兑现预期**；
- 说明"每元素两次比较"不是单线程落后的全部原因，采样成本与缓存访问模式同样是瓶颈。

**被否掉的方案**

- 只做两路、彻底删掉三路：会丢掉"重复值极快"这个真实优势，库就失去差异化；
- 按数据规模或类型静态选择：使用者不该被迫理解这些。

**【待补充】** `dup >= 2` 这个阈值后来有没有用真实数据验证过？如果有，补上那组数据。

## D3. 小数组：阈值 24，2~5 个元素用定长排序网络

**做法**：区间长度 ≤ 24 时不再递归，直接走 `small_sort`；长度 2/3/4/5 分别用
预先展开的排序网络（无分支、无循环），6 以上用插入排序。

**理由**

- 小数组上递归调用的开销（栈帧 + 采样）超过排序本身；
- 2~5 的定长网络是编译器最容易优化的形式，比较次数固定、无循环变量；
- 阈值 24 比常见的 16 偏大，因为本库的"分区前开销"（两次早退扫描 + 采样）比标准快排更重，
  多留一点给插入排序更划算。

**代价**：插入排序是 O(k²)，k=24 时最坏 276 次比较；如果阈值取大了会拖慢整体。
24 是折中值，**没有做过系统的阈值扫描实验**。

**【待补充】** 24 这个数是怎么定的？实测扫过 8/16/24/32 吗？

## D4. 递归深度上限 `2·log₂(n)`，超限切堆排序

**做法**：进入 `sort_impl` 时先 `--depth`，小于 0 就 `make_heap` + `sort_heap` 收尾。

**理由**

- 这是 introsort 的标准做法：分区退化时保底 O(n log n)，不给构造性输入留机会；
- 系数取 2 而不是 1：三路/两路划分的树高期望接近 `log₂(n)`，但常数波动更大，
  留一倍余量，避免在正常数据上过早退化到堆排序（堆排序常数大，慢）。

**代价**：堆排序段比快排慢 2~3 倍。系数给得越宽松，退化越少但兜底越晚；2 是业界常用值。

**【待补充】** 有没有试过 1.5 或 3？如果只是抄了惯例，就在面试里如实说"参照了 introsort 的通行取值"。

## D5. 每层分区前做有序/逆序早退扫描

**做法**：进入分区前，先从左往右扫一遍看是否已升序（是则直接返回），
再扫一遍看是否已降序（是则 `std::reverse` 后返回）。

**理由**

- 现实数据里"基本有序"极常见（追加写入、合并结果、数据库回填）；
- 随机数据上这两次扫描各自 1~2 次比较就退出，成本可以忽略；
- 有序输入直接 O(n)，逆序 O(n)，比任何比较排序的下界都快——这是本库相对 `std::sort` 最稳定的优势。

**代价**

- 对"几乎有序但末尾有一个逆序对"的数据，每层都要白扫一遍；
- 并行版里这个优势会被切块削弱（块越小，早退越不划算），所以有序数据的并行版（4.1 ms）
  反而比串行（1.3 ms）慢——**并行对小/有序数据没有意义，不要用**。

## D6. 并行：顶层一次切块 + 原子游标抢块

**做法**

1. `collect_ranges` 串行做顶层划分，把区间切成约 `2 × max_threads` 块，块大小按比例分配；
2. 启动至多 `max_threads` 个线程（主线程也算一个），通过 `atomic<index_t>` 游标抢块；
3. 线程创建失败就降级：剩下的块由已有线程和主线程抢完，不会死锁也不会漏块。

**为什么是 2× 块数**

块数多于线程数才有负载均衡的余地（各块大小不可能完全相等，谁先干完谁去抢下一块）。
如果块数等于线程数，一个慢块就能拖住整个 join。

**为什么线程数必须等于核数**

早期版本起 `2×max_threads` 个线程去抢这些块，等于让两倍线程争同一批核——
上下文切换和缓存抖动都会吃掉收益。改成"线程数 = 核数 + 原子游标"后，
有序/逆序数据的并行耗时从 31.2 ms 降到 4.1 ms。

**代价**

- 顶层切块是**串行**的，大 N 时可观；极小 N 直接走串行（阈值 32K）；
- 每次调用都创建线程，没有线程池。高频调用场景（每秒几十次排序）开销明显，
  这是路线图里明确列出的待办，不是疏忽。

**被否掉的方案**

- `std::execution::par`：需要 TBB 后端，破坏"零依赖"；
- 每块一个线程 + join：线程数随块数增长，小块多时线程创建成本超过排序本身。

## D7. NaN 用全序比较器，而不是"文档里写不支持"

**背景**

IEEE-754 规定 NaN 与任何值比较都为 false。原实现用裸 `<`，导致三路划分里
`a < pivot` 和 `pivot < a` 同时为假，NaN 被当成"等于枢轴"塞进等值区，**结果是错的**。
而 `std::sort` 对含 NaN 的区间本身就是未定义行为，所以这不是"和标准一致"能糊弄过去的。

**做法**

所有比较走统一的 `less<T>()`：

- 有限值 < NaN，NaN 彼此相等 → 所有 NaN 统一沉到末尾；
- 采样时 NaN 不参与均值计算（否则整段枢轴变成 NaN）；
- 整数类型走 `if constexpr` 分支，零额外开销。

**代价**：浮点路径多两次自比较判断（编译器通常能优化成一次 `ucomisd`）。

**为什么不直接拒绝编译浮点**

那会让 `double` 用户无法使用这个库，而 `double` 恰恰是数值排序的主力类型。

## D8. `static_assert` 挡非算术类型

**理由**：枢轴要用 `+` 和 `/`，传 `std::string` 会在模板深处炸出一屏看不懂的错误。
编译期拦住并给一句人话，是接口设计的一部分，不是可选项。

---

## D9. 单头文件、零依赖

**理由**：排序库的采用成本主要不在性能，在"要不要为它改构建系统"。
单文件可以 `#include` 就走，这是本库相对 TBB/Boost 的真实优势。

**代价**：没有 ABI 隔离，所有实现都在使用者编译单元里；改动会触发全量重编。

---

## D10. CMake 导出与 `find_package`

**踩过的坑**：早期只写了 `install(EXPORT ...)`，没生成 `meansortConfig.cmake`，
结果装完之后 `find_package(meansort CONFIG)` 根本找不到包——**装上去是废的**。
现在补齐 `CMakePackageConfigHelpers` + `configure_package_config_file` + 版本文件，
CI 里加了一步"安装冒烟"专门守着这条路径。

**教训**：能被安装 ≠ 能被消费。安装路径必须有测试，否则坏了没人知道。

## D11. 双许可：AGPL-3.0 + 商业授权

**理由**：AGPL 让"闭源嵌入并对外提供服务"必须购买授权，开源使用则完全免费。
这是基础设施类库的常见做法。

**现实**：个人几乎无法发现并追究违规使用，所以商业授权更接近"意向声明 + 联系方式"，
不宜当作主要收入预期。商业授权入口暂时指向 GitHub Issues。

## 已知取舍汇总

| 取舍 | 现状 | 影响 |
|---|---|---|
| 均值枢轴 | 保留 | 重尾分布切分不平衡，串行慢约 30% |
| 无线程池 | 每次调用建线程 | 高频调用场景有固定开销 |
| 仅内存内 | 不做外部排序 | 超出内存的数据无法处理 |
| 仅算术类型 | `static_assert` 拒绝 | 通用性受限，换来枢轴可用 |
| 非稳定 | 无序号保留 | 需要稳定的场景不可用 |
| 单头文件 | 全实现进使用者 TU | 重编成本高 |

## 归档的怀疑与自证

- "比 std::sort 快 2 倍"——**不成立**，那是拿并行版打单线程 `std::sort`，属于换参照系。
  同一台机器上串行仍慢 33%，见 benchmark.md。
- "自适应划分能追平 std::sort"——**没兑现**，同机 A/B 只有约 4%。
- "任何分布下单层至少切掉 5/16"——**过度声称**，16 个采样只给概率保证，已从 README 删除。

保留这一节的目的：这些是作者自己踩过的坑，面试时被问到"你这个项目有什么不足"，
这里有现成、诚实、有数据支撑的答案。
